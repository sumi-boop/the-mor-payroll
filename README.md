# THE MOR 給与明細自動作成Webアプリ

毎月のCSVを取り込み、勤怠実績と支給額から給与明細を計算・確認し、A4の給与明細PDF(個別/ZIP一括)を発行する社内向け給与明細作成アプリです。

## 1. 作成した機能

### 画面(6画面)

| 画面 | 内容 |
| --- | --- |
| ダッシュボード (`/dashboard`) | 対象年月ごとの件数・支給額合計・控除額合計・差引支給額合計・未確定件数・エラー件数・確定率などの集計を表示 |
| CSVアップロード (`/import`) | CSVファイルをアップロードし、文字コード自動判定→内容プレビュー→氏名の一致状況確認→取込確定、の3段階ウィザード |
| 従業員マスタ (`/employees`) | 従業員の登録・編集・在籍状況(在籍/休職/退職)管理(物理削除は行わない) |
| 月別控除設定 (`/deductions`) | 従業員×対象月ごとの社会保険料・所得税・住民税等を入力。前月からのコピー機能、住民税の6月〜翌年5月一括登録機能を搭載 |
| 給与計算確認 (`/payroll`) | 対象月の全従業員の計算結果と警告(エラー/注意)を一覧表示し、問題のない明細のみ選択して確定 |
| 給与明細PDF | 確定済み明細を個別PDF、または対象月まとめてZIPでダウンロード |

このほか、確定履歴・CSV取込履歴・監査ログを閲覧できる履歴画面(`/history`)も実装しています。

### 主要ロジック

- **CSV解析**: 12列固定フォーマット(氏名, 出勤日数, 労働時間, 残業時間, 深夜労働時間, 時給, 基本給, 残業手当, 深夜手当, 通勤手当, 手当・その他, 合計)を検証。列不足・列名相違・金額/時間形式の不正・数式インジェクションの可能性がある値を行単位で検出しエラー表示。
- **文字コード自動判定**: UTF-8 / UTF-8(BOM付き) / Shift_JISを自動判定してデコード(`jschardet` + `iconv-lite`)。
- **金額の正式採用**: CSVの支給額(基本給・残業手当・深夜手当・通勤手当・手当その他・合計)は勤怠時間から再計算せず、CSV記載値をそのまま正式な支給額として採用。ただし内訳合計とCSVの「合計」列が1円以上ずれる場合は「支給額不一致」警告を出し、管理者が明示的に確認(チェック)するまで取込・確定をブロック。
- **氏名照合**: 全角/半角スペースや連続空白を正規化した上で完全一致のみ自動候補とし、非一致・重複・複数候補の場合は「新規従業員として登録」「既存従業員に紐付け」「取込対象外」を管理者が明示的に選択するまで処理を進めない(あいまい一致による自動連携は行わない)。
- **確定・スナップショット**: 給与明細を確定すると、その時点の控除額を明細レコード自身へコピー(凍結)し、`PayrollSnapshot`として全項目のJSONスナップショットを保存。確定後に月別控除設定を変更しても、確定済み明細の金額は一切変化しない(統合テストで検証済み)。
- **二重登録防止**: 従業員×対象月の組み合わせにDB一意制約を設定。未確定明細への再取込は上書き更新(下書きとしての利便性)だが、確定済み明細への再取込は上書きせず「確定済みのため要手動対応」として報告する。
- **PDF生成**: `@react-pdf/renderer`でA4・1人1ページの給与明細を生成。日本語(Noto Sans JP)をPDFへ完全に埋め込み済みで文字化けなし。ファイル名は`給与明細_YYYY年MM月_氏名.pdf`、ZIP一括ダウンロードは`THE_MOR_給与明細_YYYY年MM月.zip`。
- **金額表示**: 3桁カンマ区切り+「円」表記に統一。画面配色は仕様どおり、濃紺/白/淡いグレーを基調とし、入力欄=黄色、計算結果=薄い緑、エラー=赤、未確定=オレンジで区別。

### セキュリティ

- 管理者パスワードはbcrypt(12ラウンド)でハッシュ化して保存。ログイン失敗時もダミーハッシュ比較でタイミング攻撃を軽減。
- セッションはJWT(HS256, 有効期限8時間)をHTTP Only Cookieで管理。
- CSVアップロードは拡張子(.csv)・MIMEタイプ・サイズ(5MB上限)を検証。
- CSVセル値はHTMLとして描画せず、`=` `+` `-` `@`等で始まる数式インジェクションの可能性がある値は取込エラーとして拒否。
- 監査ログ(`audit_logs`)には個人情報・金額を含まない要約のみ記録(氏名・住所・金額はログに残さない設計)。
- PDF/CSVは`public`配下に置かず、認証済み管理者のみがAPI経由でダウンロード可能。
- 従業員の物理削除は行わず、`status`(active/leave/resigned)で管理。

### Prisma構成に関する重要な設計判断

このアプリは**Prismaの「driver adapter + JS/WASMスキーマエンジン」構成**を採用しています(`prisma.config.ts`で`engine: "js"` + `@prisma/adapter-better-sqlite3`を指定、generatorは`engineType = "client"`)。これは単なる開発環境都合の妥協ではなく、以下の理由から意図的に選んだ構成です。

- Prisma標準のRustエンジン(バイナリ)を一切ダウンロードせず、`prisma generate`・`prisma db push`が**完全にネットワークアクセスなし**で完結します。
- 同じ理由で、将来Vercel等のサーバーレス環境へデプロイする際もネイティブバイナリの心配が不要です。
- 唯一のトレードオフとして、この構成では`prisma migrate dev`(マイグレーション履歴を`_prisma_migrations`テーブルに記録する完全なワークフロー)が現状のPrisma側の制約(JS版スキーマエンジンの未成熟な部分)によりP1014エラーで失敗するため、本プロジェクトではスキーマ同期に`prisma db push`を採用しています。マイグレーション履歴ファイルは生成されませんが、`schema.prisma`自体がスキーマの正とみなせるため運用上の実害はありません。将来的にPrismaの当該制約が解消された場合は、`prisma migrate dev`への切り替えも可能です。

### better-sqlite3のネイティブビルドに関する対応

`@prisma/adapter-better-sqlite3`はデフォルトで`better-sqlite3@^11.x`系(ソースビルドが必要な古いバージョン)に依存しますが、本プロジェクトは`package.json`の`overrides`で`better-sqlite3`を`^13.0.3`(全主要プラットフォーム向けのプリビルド済みバイナリをnpmパッケージ自体に同梱)へ強制的に統一しています。これにより、

- `npm install`時にネイティブコンパイル(node-gyp)が一切走らず、ビルドツール(Python/gcc等)が入っていない環境でも確実にインストールできます。
- ネットワーク制限のある環境(GitHubやnodejs.org等への外部通信が制限された環境)でもインストールが失敗しません。

この対応により、ほとんどの環境では`npm install`のみでネイティブコンパイルなしにセットアップが完了します。ただし、npm自体の仕様(`binding.gyp`ファイルが存在するパッケージに対し、`gypfile: false`の指定に関わらずインストール時に`node-gyp rebuild`を暗黙的に試みることがある挙動)により、環境によっては同梱済みのプリビルドバイナリがあるにもかかわらず不要なネイティブビルドが走ろうとする場合があります(通常のインターネット環境では自動的にビルドが成功するため問題になりませんが、ビルドツールやGitHub/nodejs.orgへの通信が制限された環境では失敗することがあります)。その場合は[3. 起動方法](#3-起動方法)に記載の`--ignore-scripts`を使ったインストール手順を使用してください。これは本プロジェクトの検証環境(ネットワークが制限されたサンドボックス)で実際に発生し、確認・解決した事象です。

## 3. 起動方法

### 前提

- Node.js 22以上

### 手順(通常の環境)

```bash
# 1. 依存パッケージのインストール
#    (postinstallで `prisma generate` が自動実行されます)
npm install

# 2. 環境変数ファイルを作成
cp .env.example .env
# 必要に応じて SESSION_SECRET を変更してください(本番運用前は必須)

# 3. データベースのセットアップ(スキーマ反映 + 初期管理者ユーザー作成)
npm run db:setup

# 4. 開発サーバーを起動
npm run dev
```

ブラウザで `http://localhost:3000` を開いてください。

### 手順(`npm install`でネイティブビルドエラーが出る場合)

社内プロキシ等でGitHub/nodejs.orgへの通信が制限されている環境では、`npm install`の際に`better-sqlite3`のネイティブビルド(`node-gyp rebuild`)が試みられ失敗することがあります(本プロジェクトが同梱するプリビルド済みバイナリを使えば本来ビルドは不要です)。その場合は以下の手順を使用してください。

```bash
# 1. スクリプト実行なしでインストール(ネイティブビルドを試みない)
npm install --ignore-scripts

# 2. Prisma Clientを手動生成(ネットワーク通信なしで完了します)
npx prisma generate

# 3. 以降は通常どおり
cp .env.example .env
npm run db:push
npm run db:seed
npm run dev
```

### 本番ビルド

```bash
npm run build
npm run start
```

本番ビルド(`next build`)・本番起動(`next start`)ともに正常に動作することを確認済みです。

## 6. 残っている注意点

- **パスワード変更UI未実装**: 管理者が画面からパスワードを変更する機能は未実装です。初期パスワードの変更が必要な場合は、シード実行前に`ADMIN_PASSWORD`環境変数を設定するか、DBを直接更新してください。
- **`prisma migrate dev`は使用不可**: [2. 採用した構成](#2-採用した構成)に記載の通り、本構成では`prisma db push`でスキーマを同期します。マイグレーション履歴ファイル(`prisma/migrations/`)は生成されないため、複数人での開発でスキーマ変更を追跡したい場合は、将来的な運用ルールの検討が必要です。
- **npm audit: 中程度のリスクの脆弱性1件**: `prisma`が依存する`@prisma/config`経由で`deepmerge-ts`に既知の脆弱性(悪意ある深いオブジェクトのマージによるスタック枯渇/DoS)が報告されています(`npm audit`で確認可能)。これは開発時のPrisma CLI設定読み込みに関わる依存であり、アプリの実行時にエンドユーザーからのリクエストを処理する経路には含まれないため、実害は限定的と考えられますが、`npm audit fix --force`によるPrismaの強制ダウングレードは本プロジェクトのdriver adapter構成を壊す可能性があるため未適用です。Prismaの新バージョンでこの依存が解消され次第、更新を推奨します。
- **メール通知・エクスポート等の周辺機能は未実装**: 仕様に明記されていない範囲(例: 給与明細のメール送付、CSVでの給与データエクスポート、複数管理者の権限分離)は今回のスコープに含めていません。
- **デプロイ構成**: [DEPLOY.md](./DEPLOY.md)にRenderへのデプロイ手順と`render.yaml`を用意しています。Renderは`*.onrender.com`ドメインでHTTPSを自動的に有効化するため、別途証明書の設定は不要です。他のホスティング先を使う場合は、HTTPS終端の設定を別途行ってください。現在`render.yaml`は**Starterプラン(月$7.25程度、永続ディスクあり)**で構成しており、再デプロイやアクセスの空白時間があっても保存データは消えません。
- **`render.yaml`: db push/seedをpreDeployCommandではなくstartCommandに配置**: Render公式仕様として、`preDeployCommand`は実際にサービスが起動するインスタンスとは別の一時的な環境で実行され、永続ディスクにアクセスできない(ディスク上のデータベースファイルへの変更が反映されない)。この仕様に気づかず`preDeployCommand`側に`prisma db push`/`db:seed`を置いた結果、実運用インスタンス側のデータベースにテーブルが作成されずログイン不能になる不具合が実際に発生したため、`startCommand`側に移動して修正済み。両コマンドとも冪等なため、起動のたびに実行しても安全。
- **`render.yaml`: startCommandは`sh -c "..."`で明示的に囲む**: Renderダッシュボードで`startCommand`を直接編集して保存した場合、`"cmd1 && cmd2 && cmd3"`のように`&&`で連結しても、シェル経由で解釈されず1つ目のコマンドしか実行されない(結果、db:seed・next startが実行されない)不具合を実機で確認した。`sh -c "cmd1 && cmd2 && cmd3"`のように明示的にシェルを指定することで解決する。`render.yaml`経由でのBlueprintデプロイでは発生しない可能性もあるが、念のため両方のケースで安全な`sh -c`形式を採用している。
- **`package.json`の依存関係配置**: Render等の一部ホスティング環境では、ビルド時に`devDependencies`がインストールされない場合があります(本番ビルドの高速化のための一般的な仕様)。そのため、ビルドに必要な`typescript`・`@types/*`・`tailwindcss`・`tsx`等は`dependencies`側に配置しています(ローカル開発専用の`vitest`等のみ`devDependencies`のままです)。この構成でクリーンな本番相当インストール(`npm install --omit=dev`)からのビルド成功を検証済みです。
- **SQLiteのスケール**: 現状SQLite(ファイルDB)を採用しているため、同時書き込みが多い大規模運用ではPostgreSQL等への移行を検討してください(Prismaのdriver adapter構成のため、アダプタの差し替えで比較的移行しやすい設計です)。また、SQLite+永続ディスクの構成上、Webサービスのインスタンスは1台構成が前提です(複数台への水平スケールは想定していません)。社内の小〜中規模利用では通常問題になりません。

## 7. 給与計算・税務上、手動確認が必要な項目

本アプリは「CSVに記載された支給額をそのまま正式採用し、勤怠時間から再計算しない」という設計方針です。これは仕様上の要件どおりですが、裏を返すと**支給額そのものの正しさはCSVを作成する時点の計算(別システムや表計算での計算)に依存**します。以下は本アプリの範囲外であり、運用担当者による確認が必要です。

- **CSVの支給額計算そのものの正確性**: 基本給・残業手当(法定割増率25%以上等)・深夜手当(25%以上)・休日出勤手当などが、労働基準法や36協定・就業規則に照らして正しく計算された上でCSVに記載されているかどうかは、本アプリでは検証していません(内訳の合計と「合計」列の整合性のみをチェックします)。
- **社会保険料・雇用保険料の料率**: 月別控除設定画面で入力する健康保険料・介護保険料・厚生年金保険料・雇用保険料は、標準報酬月額や最新の保険料率表に基づいて管理者が算出し入力する前提です。本アプリは入力された金額をそのまま使用するのみで、料率テーブルとの自動照合は行いません。
- **所得税(源泉徴収税額)**: 「月別控除設定」画面の所得税欄に**自動計算(甲欄のみ)**ボタンを追加しました。対象年月のCSVが取込済みで、従業員が甲欄(扶養控除等申告書提出あり)の場合、国税庁公表の令和8年分源泉徴収税額表(月額表・甲欄、電算機計算の特例の算式)に基づいて概算額を計算し、所得税欄に自動入力します(`src/lib/payroll/incomeTax.ts`、算式は税額表の実データと突き合わせて検証済み・`incomeTax.test.ts`参照)。ただし以下は自動計算の対象外で、従来どおり手入力が必要です。
  - **乙欄の従業員**(2か所以上から給与を受けている場合など)、および扶養控除等申告書が未提出の従業員: 電算機計算の算式を公式資料から確実に検証できなかったため未対応です。ボタンを押すと「対応していません」というメッセージが表示されます。
  - **通勤手当の非課税限度額**: 自動計算では通勤手当を全額非課税として扱っています。月15万円などの非課税限度額を超える通勤手当を支給している場合は、超過分を課税対象に加えて再計算するなど、手動での調整が必要です。
  - 自動計算はあくまで概算であり、入力後も「所得税」の確認チェックは自動では付きません(必ず内容を確認したうえでチェックしてください)。
  - 毎年、国税庁が源泉徴収税額表を改定する可能性があるため、年が変わったタイミングで`src/lib/payroll/incomeTax.ts`内の数値が最新の公表資料と一致しているか確認してください。
- **住民税(特別徴収)**: 「住民税の月別反映」機能は、市区町村から届く特別徴収税額決定通知書の金額を6月〜翌年5月の12ヶ月分まとめて入力する補助機能です。金額そのものの正しさ(通知書との突合)は運用担当者が確認してください。
- **年末調整・賞与・退職金**: 本アプリは月次給与明細の作成のみを対象としており、年末調整計算や賞与明細・退職金明細には対応していません。
- **雇用契約上の区分(時給/月給)や割増率の従業員ごとの違い**: `Employee.payType`等のフィールドは用意していますが、実際の計算(CSV作成側)に反映されているかどうかは運用側でご確認ください。
